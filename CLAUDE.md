# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A job dispatch system (customer → dispatcher → business owner → technician → customer confirms + rates). One responsive Next.js app, phone-first, deployed to Vercel at https://workflow.aihuachen.com. See README.md for the product rationale and the demo run-through script.

## Commands

Package manager is **pnpm** (pinned via `packageManager` and `corepack`). Node 22+.

- `pnpm dev` — Next.js dev server with Turbopack (port 3000)
- `pnpm test` — Vitest, runs once. `pnpm test:watch` re-runs on save. Vitest only picks up `*.test.ts`, not `*.e2e.ts`.
- `pnpm test:e2e` — Playwright headless (phone + laptop projects, Pixel 7 + Desktop Chrome). To run one project headed: `pnpm exec playwright test --headed --project=laptop`. To run a single test, pass the file path and `-g "<title>"`. Playwright starts `pnpm dev` itself if 3000 is free and reuses an existing one otherwise.
- `pnpm typecheck` — `tsc --noEmit`. `pnpm build` — production build. `pnpm format` — Prettier.
- Database: `pnpm db:migrate` (dev-branch migration), `pnpm db:deploy` (apply saved migrations, used for `main`), `pnpm db:seed` (demo data; keeps user-created jobs), `pnpm db:reset-demo` (wipes **all** jobs and customers, then seeds), `pnpm db:studio`.

Everything local runs against the Neon **`dev` branch** (connection string in `.env.local` as `DATABASE_URL`, pooled host). Never commit `.env.local` or paste the string in chat.

### Updating the live database (`main`)

Migrations do not run on deploy. When a commit adds a migration or live demo data needs resetting, run `db:deploy` / `db:seed` / `db:reset-demo` locally with a one-shot env override **before pushing**:

```bash
read -rs "MAIN_URL?Paste main's connection string: "; echo
DATABASE_URL_UNPOOLED="$MAIN_URL" pnpm db:deploy
```

`prisma.config.ts` prefers `DATABASE_URL_UNPOOLED` and otherwise strips `-pooler.` from `DATABASE_URL`. A variable typed on the command line wins over `.env.local`, so the override targets `main` without touching the file.

## Architecture

### One Next.js app, App Router, route groups

- `app/(public)/` — customer-facing routes (`/`, `/request`, `/track/<token>`). No auth, no middleware gate.
- `app/(app)/` — staff routes (`/dispatch`, `/jobs`) inside the app shell.
- `app/api/` — server endpoints. One generic staff action endpoint `POST /api/orders/<id>/actions` drives every staff button; `POST /api/track/<token>/actions` is the customer's. `/api/ratings` is the standalone ratings endpoint.
- `middleware.ts` gates staff paths (`/dispatch/*`, `/jobs/*`, `/api/session/*`, `/api/orders/:id/actions`) with HTTP Basic auth when `DEMO_PASSWORD` is set; otherwise it's a no-op. Customer pages stay open so QR scans work. Compares in constant time.

Path alias `@/*` points at the repo root (see `tsconfig.json`). `strict` + `noUncheckedIndexedAccess` are on.

### Business-logic layer in `lib/<area>/`

**All database access lives in `lib/`. Pages and API routes call `lib/` functions; never import `@/lib/db` outside `lib/`.** This is how the "every query filters by `businessId`" rule is kept in one place.

- `lib/db.ts` — the single Prisma client (reused across HMR in dev).
- `lib/orders/status.ts` — the state machine: allowed transitions and who may make them. **Pure, no I/O.** Pages call `nextActions(order, actor)` so they only render buttons the server would accept.
- `lib/orders/transition.ts` — `applyAction` wraps status.ts + the database write + the OrderEvent (history row) in one transaction. The update is conditional on the order still being in the same state it was when read, so concurrent writers get a `conflict` refusal instead of a lost update. Refusal reasons are typed (`status` → 409, `person` → 403, `input` → 400, `not_found` → 404, `conflict` → 409); the HTTP mapping is in `lib/orders/http.ts`.
- `lib/orders/{request,tracking,queries,create}.ts` — input validation (pure, tested), timeline for the tracking page (pure, tested), and the Prisma query helpers.
- `lib/ratings/{input,queries}.ts` — same split: pure `input.ts` (tested in `pnpm test`), DB in `queries.ts`.
- `lib/session.ts` — demo sign-in: a `demo_user` cookie set by the account switcher, no password. `getCurrentUser()` + `toActor()` are the two entry points; replacing them is how real auth lands in the pilot.
- `lib/generated/prisma/` — Prisma's generated client, regenerated by `postinstall` (`prisma generate`). **Not committed.** Import types from here (`@/lib/generated/prisma/enums`, `@/lib/generated/prisma/client`), not from `@prisma/client`.

### Data model (`prisma/schema.prisma`)

Business, User (DISPATCHER / OWNER / TECHNICIAN; dispatchers have `businessId: null`), Customer, Order, OrderEvent (history, one row per status change with `actorUserId`), Rating. Every multi-tenant row carries `businessId`. Customers don't sign in — the Order's `trackingToken` is their key.

### State machine summary

New → Offered → Accepted → Scheduled → On the way → In progress → Done → Confirmed (final) or Problem reported → Scheduled again. Cancelled is final. Decline/withdraw returns the job to New and clears `businessId`. Owners act only on their business's jobs; technicians only on jobs assigned to them. Full table is in README "Order workflow: who can change a job's status".

### Live refresh

Staff and tracking pages poll every 30s via `components/AutoRefresh.tsx`. Refreshes pause when the tab is hidden and stop once the job is Confirmed or Cancelled; typing in a field is preserved.

## Tests

- **Unit** (`pnpm test`, Vitest): colocated `*.test.ts` next to the pure modules they cover — the state machine, request/tracking/rating input, formatters. These don't hit the database.
- **End-to-end** (`pnpm test:e2e`, Playwright): `e2e/full-job.e2e.ts` plays the full customer → dispatcher → owner → technician → customer-confirms-and-rates script in separate browser contexts, once at Pixel 7 size and once at desktop size. Runs against the dev database and cleans up after itself. `e2e/db.ts` is a tsx-loaded Prisma helper (Playwright's loader can't load the generated client directly). **Name e2e files `*.e2e.ts`** so Vitest skips them.
- Playwright uses the Chrome installed on the machine (`channel: "chrome"`); no browser download.

## Conventions that aren't obvious from the code

- **MUI + Emotion only**, style via the theme in `theme/theme.ts` and `sx` props. No separate stylesheets. (See README "Styling" decision.)
- The dispatcher's offer dialog, owner actions, and technician buttons are all rendered from `nextActions(order, actor)` — don't hard-code button visibility in a page; extend the state machine instead.
- When adding a schema change: `pnpm db:migrate --name what_changed` (hits dev only), commit the generated `prisma/migrations/*` directory, and remember to run `pnpm db:deploy` against `main` before pushing (see "Updating the live database" above).
